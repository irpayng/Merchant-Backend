# Merchant settlement config aligned with super-merchant

The merchant dashboard now fetches settlement configuration from the same authoritative source as super-merchant: gRPC calls to tms-config for settlement type and settlement accounts. The frontend layout matches super-merchant's structure with flex-col InfoRows, 2-column grids, and a full-width accounts card.

**Watch for:** Nothing blocking. The implementation correctly mirrors the super-merchant pattern. MSC fields maintain backward compatibility by still reading from the legacy `supermerchant.settlement_configs` table.

**Verdict**: APPROVED

## High-level view

The backend controller now makes two gRPC calls instead of relying on local data: `getMerchantSettlementType()` for the settlement schedule and `listMerchantSettlementAccounts()` for the account pool. MSC fields (msc_pos_percentage, instant_transfer_fee, monthly_terminal_fee) continue to read from the legacy cross-schema query for backward compatibility during migration.

The frontend restructures the layout to match super-merchant: InfoRow uses flex-col with label above value, cards use 2-column grids with gap-x-6, and the Settlement Accounts card spans the full width with the same list styling and "Add Account" modal workflow.

### gRPC integration for settlement data

The backend controller uses two gRPC methods from the config service:

```java
// Settlement type from authoritative source
Map<String, Object> settlementTypeResult = grpcClient.getMerchantSettlementType(merchantId);
if (Boolean.TRUE.equals(settlementTypeResult.get("found"))) {
    builder.settlementType((String) settlementTypeResult.get("settlement_type"));
    foundSettlementType = true;
}

// Settlement accounts from pool
List<Map<String, Object>> accounts = grpcClient.listMerchantSettlementAccounts(merchantId);
```

This mirrors the super-merchant SettlementConfigService pattern where settlement configuration is read from tms-config rather than stored locally.

### MSC backward compatibility

The MSC fields still read from the legacy table via cross-schema native query:

```java
Object[] row = (Object[]) entityManager
    .createNativeQuery("SELECT msc_pos_percentage, instant_transfer_fee, monthly_terminal_fee "
            + "FROM supermerchant.settlement_configs WHERE user_id = :userId")
    .setParameter("userId", merchantId).getSingleResult();
```

This maintains compatibility during the migration period when MSC data hasn't been moved to tms-config yet.

### Frontend layout alignment

The merchant-fe SettlementConfig component now matches super-merchant-ui's structure:

1. **InfoRow component** - Uses `flex flex-col gap-1 py-3` with label in muted text-xs and value in text-sm font-medium
2. **Card grids** - Uses `grid grid-cols-2 gap-x-6 gap-y-1` for the 2-column layout within cards
3. **Accounts card** - Spans full width with `lg:col-span-2`, contains account list with the same row structure (icon, name with badges, bank/number)
4. **Add Account modal** - Uses the same form structure with bank select, account number, and account name inputs

### hasConfig determination

The `hasConfig` flag is now set correctly based on whether data was found:

```java
builder.hasConfig(foundSettlementType || foundAccounts);
```

This returns the appropriate empty state when a merchant has no settlement configuration.
