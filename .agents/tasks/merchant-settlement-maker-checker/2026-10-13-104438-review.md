# Merchant Settlement Maker-Checker Implementation

Implements a maker-checker workflow where merchants can request settlement account changes via Merchant-Backend, and super-merchant (bank) admins approve via the existing approval system. The implementation uses native SQL from Merchant-Backend to write directly to `supermerchant.pending_approvals` with new columns that distinguish merchant-initiated requests from admin-initiated ones.

**Watch for:** No blocking concerns identified. Implementation correctly handles null `maker` for merchant-initiated requests (confirmed), cross-schema inserts use proper native SQL (confirmed), and the approval flow gracefully adapts to merchant-initiated requests (confirmed).

**Verdict**: APPROVED

## High-level view

The PendingApproval entity in super-merchant gains three new nullable fields (`merchant_initiated`, `merchant_name`, `merchant_email`) and allows `maker_id` to be null. When `merchant_initiated` is true, the `toSettlementDto()` method uses the merchant's stored name/email as the maker info instead of dereferencing a null `maker` relation.

Merchant-Backend introduces a `SettlementApprovalService` that resolves the merchant's bank from their TID assignments, checks for duplicate pending requests, and inserts directly into `supermerchant.pending_approvals` using native SQL with the new merchant-initiated fields populated. The controller exposes two endpoints: POST for submitting requests and GET for listing them.

The bank-scoped approval/reject logic in super-merchant's `ApprovalService` continues to work because it checks `bank_code` from the approval record rather than requiring a non-null `maker`. No changes were needed to those methods.

### Super-merchant schema and entity changes

The `PendingApproval` entity adds:
- `@Column(name = "merchant_initiated") @Builder.Default private Boolean merchantInitiated = false`
- `@Column(name = "merchant_name", length = 255) private String merchantName`
- `@Column(name = "merchant_email", length = 255) private String merchantEmail`
- `@JoinColumn(name = "maker_id", nullable = true)` — was `nullable = false`

The admin-schema.sql includes idempotent ALTER TABLE statements:
```sql
ALTER TABLE supermerchant.pending_approvals ALTER COLUMN maker_id DROP NOT NULL;
ALTER TABLE supermerchant.pending_approvals ADD COLUMN IF NOT EXISTS merchant_initiated BOOLEAN DEFAULT FALSE;
ALTER TABLE supermerchant.pending_approvals ADD COLUMN IF NOT EXISTS merchant_name VARCHAR(255);
ALTER TABLE supermerchant.pending_approvals ADD COLUMN IF NOT EXISTS merchant_email VARCHAR(255);
```

### Approval service adaptation

The `toSettlementDto()` method now handles merchant-initiated requests:

```java
boolean merchantInitiated = Boolean.TRUE.equals(approval.getMerchantInitiated());
String makerName;
String makerEmail;
if (merchantInitiated) {
    makerName = approval.getMerchantName();
    makerEmail = approval.getMerchantEmail();
} else {
    makerName = approval.getMaker() != null ? approval.getMaker().getName() : null;
    makerEmail = approval.getMaker() != null ? approval.getMaker().getEmail() : null;
}
```

This avoids NPE when `maker` is null and populates the DTO fields used by the approval UI.

### Merchant-Backend request submission

`SettlementApprovalService.submitAccountChangeRequest()` performs:
1. Bank code resolution from `tids` table via native query
2. Duplicate check against `supermerchant.pending_approvals`
3. Native INSERT with `merchant_initiated=true, merchant_name, merchant_email` populated

The INSERT correctly omits `maker_id` (it defaults to NULL) and sets `version=0` for optimistic locking compatibility.

### DTOs and validation

`SettlementAccountRequestDto` uses `@NotBlank` validation for all required fields and `@JsonProperty` for snake_case serialization. `ApprovalRequestResponse` follows the same pattern for listing approval requests back to the merchant.

### Controller endpoints

- `GET /settlement-config/requests` — lists the merchant's approval requests, scoped by `merchantId` from `MerchantScope`
- `POST /settlement-config/request-account` — submits a new request, returning the approval ID

Both use `@Transactional` appropriately (write for POST, `readOnly = true` for GET).
